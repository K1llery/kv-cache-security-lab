# problem.md — 问题陈述

> 状态：骨架（2026-09-27）。依据：`集大成_项目总览与迁移指南_20260926.md` §3、a3、10 号文件。
> 本文件只写已核验的事实与正式定义；凡是推测必须带"假设"标记。

## 1. 场景

多轮对话 / RAG / Agent 负载中，KV Cache 以 AES-GCM 块加密存放于 SSD / 对象存储（LMCache 2026-08 已上线的 L2-at-rest 加密属此类）。新请求命中已缓存前缀时的恢复路径为：

```
取回密文 → 解密认证 → 传入 GPU → 继续推理（出首 token）
```

工业证据（需求真实存在，不证明瓶颈存在）：Mooncake（FAST'25，Kimi 生产平台）、Apple PCC Stateless Inference（prefill→decode 加密 KV 交接、多轮加密 KV 复用）、LMCache 官方加密博客（2026-08-19）。

## 2. 研究问题（a3 §RQ1–RQ3，已冻结）

- **RQ1（测量）**：外部加密 KV 恢复中，等待主要发生在**读取、解密认证、完成通知、CPU→GPU 传输、请求调度**哪一段？这些等待何时落在 TTFT 关键路径上？
  - 直接检验对象：LMCache 官方博客断言 *"encryption cost hides behind storage latency instead of adding to TTFT"*（未提供负载条件与测量方法）。
- **RQ2（机制）**：在 verified-before-use、相同 CPU/缓冲预算下，把**认证记录粒度 / I/O 批次 / 对消费者的完成通知**三者解耦，是否优于强基线（细粒度 AEAD + 批量 I/O + 固定预取）？
- **RQ3（边界）**：命中比例、未缓存后缀长度、并发、存储速度变化时，逐层安全恢复何时不如整体恢复或重算？

## 3. 威胁模型（10 号文件，可向导师讲清的版本）

- **信任**：推理进程、模型、主机系统、密钥服务、本地 CPU/GPU 内存。
- **不信任**：外部缓存存储与传输路径——可被观察、篡改、调换、删除、回放。
- **目标**：保护缓存内容机密性；保证只有当前请求所预期且通过认证的记录进入计算。
- **非目标（第一版）**：访问模式/对象长度/索引泄漏、拒绝服务、防恶意宿主机的机密计算、KV 量化、淘汰算法、多写者。
- **明确不声称**：具备 TEE 级机密计算能力；AAD 缺失=生产漏洞（只证明组件级保证范围，全链路核查后才能定性——a3 的表述）。

## 4. 安全语义铁律（不可妥协，来自总览 §3）

1. verified-before-use：未通过 AEAD 认证的明文绝不进入模型；
2. 对象身份绑定：模型/布局版本/前缀身份/层号/位置长度写入 AAD 或经认证清单校验（当前 LMCache AAD=None——源码核验：aesgcm.py L78/L130，提交 9a7b605）；
3. 经认证的对象清单防截断/整对象替换/旧版本回放（epoch 写进文件不足以防回滚）；
4. nonce 不重复；第一版只用不可变对象 + 成熟密钥管理，不做原地覆盖；
5. 某层所需任一块失败 → 终止该请求、丢弃临时状态，不提交不完整恢复的输出。

## 5. 已核验的实现缺口（本题的"现象"来源，组件级已复核）

| 源码事实（LMCache@9a7b605 / vLLM@3b4566c） | 影响 |
| --- | --- |
| AESGCM encrypt/decrypt 的 AAD=None；密钥仅由 cache_salt HKDF 派生 | 同 salt 同长度对象替换在 serde 边界被接受（组件原型 B4 已复核） |
| `_run_task` 对一批对象循环逐个处理，任务结束只记一个 success 并通知一次 | "块已认证但消费者不可用"的状态真实存在（组件原型 B5 已复核） |
| serde_wrapper：读取完成→解密提交→解密完成两道边界 | 完成通知粒度与认证粒度是两个变量 |
| MP 连接器 `wait_for_layer_load` 为空实现；v1_adapter 有真实逐层钩子 | 加密路径与逐层加载当前不能直接组合（集成缺口） |
| vLLM 调度门控：等远程 KV 的请求不分配新计算 | 通知边界直接影响请求何时恢复计算 |

**尚未证实**：上述缺口在端到端路径中造成有价值的 TTFT 损失（a3 明确：这是待验证问题，不是已成立论文问题）。→ 由 exp_004 / RQ1 回答。
