# exp_008 结论（2026-09-27 下午）：修正版引擎级 TTFT 对照

## 对评审意见第 1 项的回应

exp_006 的"重算"组被证实命中了缓存（提示词只改尾部，服务端日志显示相应请求 4/4、19/19 L2 命中）
——exp_006 的全部引擎级结论作废。本实验以四项修正重测：

1. 重算组 = 全新 cache_salt（逐次记录于 raw jsonl 的 `salt_used`），并**逐请求断言**：
   本请求 id 的 Prefetch 行必须无 retained>0（全部通过）；
2. 提示词以 token-id 数组下发，长度即实测分词长度（1024/5000/8192）；
3. 每次正式请求前清 L1（命中状态一致）；
4. 异步写完成 = 轮询 "Stored" 日志行 + 落盘对象数达期望且稳定（run1 曾因等待不足出现
   8/32 部分命中并被断言捕获——修正后重跑）。

服务端 `Retrieved` 窗口：1024 token ≈ 0.08–0.1s；4864 token ≈ 0.45–0.52s。

## 这告诉了我们什么

1. **引擎里不存在 crossover**：三个点（1K/5K/8K）上 L2 命中都慢于真重算
   （2.3×/2.9×/2.5×，AES-GCM 栈）。主因不是认证，而是恢复路径自身的安装开销
   （服务端 Retrieved 0.1s/Ktoken 量级 + vLLM 侧 scatter/paged 安装）。
2. **明文 L2 命中同样慢于重算**（8192：960 vs 350ms）——把认证完全拿掉，引擎恢复路径
   仍不具竞争力。认证组织优化在这条路径上没有可改善的 TTFT 空间。
3. **明文 vs AEAD 差异微弱且分布重叠**：中位差 +8.4%（5K）、+7.5%（8K）、-11%（1K，明文更慢），
   min/max 大面积交叠（明文 8192 最大 1925ms > AEAD 最大 1445ms）。
   不构成"稳定的、可归因的认证关键路径开销"。
4. run1→run2 的重算中位有漂移（P8192：326→417ms），各对照组间比较必须在同 run 内进行
   ——本表全部来自同一 run（run2）。

## 局限

- 只覆盖 1K/5K/8K；更长前缀未测（受 12GB 显存与 LMCache 安装开销线性增长约束，
  若要找引擎 crossover 需在更大显存机器上继续外推）。
- n=10（l2hit/recompute）起步量级；P8192 明文栈有 1 个 1925ms 离群值（保留未删）。
- 引擎内未做逐层插桩（scatter/H2D 分解需 patch，列为未测环节）。
